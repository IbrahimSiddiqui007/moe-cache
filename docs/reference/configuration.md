# Configuration (environment variables)

**The first table is the list of common options; the second part ("Settings not listed above") covers every other `MOE_CACHE_*` name the code reads (175 in all).** `tools/env_names_check.py` checks that every name the code reads is mentioned in the docs. Defaults below are those of the code on 2026-11-03.

`moe-cache-server` and the control page set these for you. Launcher options are not environment variables and are listed by `moe-cache-server --help`; one of them is new in v0.3.8 and on by default from 32k context: the long-prompt mode (`--long-prompt` asks for it at any context, `--no-long-prompt` turns it off; page: **Long-prompt mode**) sets `-ub 4096` and the q8_0 KV cache when the card has room for it, see [INSTALL.md](../guides/install.md) (speed options).

### Launcher options the help text explains briefly

| Option | What it does |
|---|---|
| `--load-method auto\|preload\|path` | How the plugin is loaded into llama-server (`auto` picks between the two the same way): `preload` = `LD_PRELOAD` for llama-server builds that link ggml directly (distro packages; not on Windows); `path` = `GGML_BACKEND_PATH` for builds with separate backend files (official releases). Defined identically on three subcommands (`server`, `learn`, `diffusion`); the definitions do not conflict — each subcommand passes its own value to the same `load_env()`. |
| `--cpu-gpu-split [auto\|FRACTION]` | Opt-in, CUDA only, dense models only, with the FFN weights in RAM (see `--no-ffn-ram`): the GPU also computes part of the rows of those weights while the CPU computes the rest (the weights go over PCIe by DMA from page-locked RAM). Needs the kit's llama.cpp with patch 0091; other builds and Vulkan are not applied. `auto` follows the measured wait; a number from 0.05 to 0.6 fixes the GPU's share. The server then loads without mmap and without repacking. |


| Variable | Meaning |
|---|---|
| `MOE_CACHE_SIZE_GIB` | cache size in GiB, or `auto` (size from the memory limit) |
| `MOE_CACHE_AVAIL_KEEP_GIB` (plugin; the launcher sets it) | the cache follows the system's available RAM while the server runs: under this many GiB it gives experts back, about 1 GiB over it it takes them back slowly (256 MiB a second); default: off on Windows (as in v0.3.8; `MOE_CACHE_LIVE_FOLLOW=1` makes the launcher set max(4 GiB, 12.5 % of the RAM)); on Linux the launcher sets that value; unset or 0 = off. It can only give back the cache's own memory; it runs while graphs compute (not while idle), not on the Linux file-view cache, and only with `MOE_CACHE_SIZE_GIB=auto`. Where it follows, the plugin prints a `moe-cache: mem:` line every 15 s (on the Linux file-view cache it prints one "live RAM follow is OFF" line at start instead, and `MOE_CACHE_AVAIL_KEEP_GIB` has no effect) (every 5 s under the line) with available RAM, the process's working set split into private and mapped files, and the cache budget |
| `MOE_CACHE_MMAP_SPIKE` (launcher) | `1` turns on the whole-file rule for a dense model on Windows: `--load-mode none` instead of mmap when the whole file plus the prompt cache would leave less than the reserve (default off, not measured at a large spill) |
| `MOE_CACHE_LIVE_FOLLOW` (launcher) | `0` stops the launcher from setting `MOE_CACHE_AVAIL_KEEP_GIB`; on Windows it is not set by default (live RAM follow is off), `1` turns it on |
| `MOE_CACHE_STREAM_GIB` (launcher) | GiB kept free in addition when the model file is bigger than the cache (default 2, not measured); 0 turns it off |
| `MOE_CACHE_RAM_GIB`, `MOE_CACHE_MARGIN_GIB` | override the detected memory limit; memory to keep free (default 1 GiB). On Windows and on Linux without a cgroup limit the launcher also sets `MOE_CACHE_RAM_GIB` itself (the RAM available at the start minus max(4 GiB, 12.5 % of the RAM), and 2 GiB less when the model file is bigger than the cache, at least 4 GiB; `MOE_CACHE_STREAM_GIB` changes that 2 GiB, an assumption not yet measured; fixed for the run: with the variable set the plugin does not read the available RAM again after the upload) unless you give `--ram` or set it. The launcher's `--ram` sets `MOE_CACHE_RAM_GIB`: **it is a sizing hint for the cache, not a RAM cap** (Windows: no limit is set on the default path, see [WINDOWS.md](../guides/windows.md); Linux: the launcher sets no limit either, only a cgroup you set yourself, such as `systemd-run -p MemoryMax=` or a unit file, is a hard limit) |
| `MOE_CACHE_GGUF` | model file (split models: the first part) |
| `MOE_CACHE_PROFILE` / `MOE_CACHE_WARM` | learn expert usage here and warm-start from it / warm start only |
| `MOE_CACHE_STATS=1` | print hit rate, reads and evictions at exit |
| `MOE_CACHE_EXEC_FUSE=0` | turn off the fused gate+up executor job (on by default since 0.3.2: same text; RESULTS 73; speed numbers follow in a later release) |
| `MOE_CACHE_IDLE_REBALANCE=0` | turn off the idle cache refill (on since 0.3.3: refills the RAM cache while an agent pauses; every PC pair won) |
| `MOE_CACHE_POLICY=classlru` | frequency-aware cache replacement instead of LRU (opt-in; paired runs in RESULTS 73; speed numbers follow in a later release) |
| `MOE_CACHE_STATS_SIGNAL=1` | print one `moe-cache-stats {json}` line of the running counters on request: Linux `kill -USR1 <pid>`, Windows set the named event `Local\moe-cache-stats-<pid>` |
| `MOE_CACHE_DISABLE=1` | load nothing: the server behaves exactly like stock |
| `MOE_CACHE_EXEC=0` | switch the expert executor off (default on) |
| `MOE_CACHE_EXEC_ECORES=N` | let the executor use N efficiency cores as well (the launcher sets up to 4 on hybrid Intel CPUs; `--no-ecores` to disable) |
| `MOE_CACHE_EXEC_THREADS=N`, `MOE_CACHE_EXEC_READERS=N` | compute threads (default: what llama.cpp asks for) and background reader threads (default 4) |
| `MOE_CACHE_RAM_LOCK=1` | default off, Linux only. Locks the cache's private memory (mlock2 on fault) so the kernel cannot swap it. Needs `ulimit -l unlimited` / `LimitMEMLOCK=infinity`; if the limit is hit it says so once and carries on unlocked |
| `MOE_CACHE_DROP_READAHEAD=1` | default off, Linux only. After the startup fill, drops the model files' page cache copy (posix_fadvise DONTNEED). Not done in file-view mode (there the page cache is the cache) |
| `MOE_CACHE_GPU_SUM=0` | turn off the GPU sum: on by default since 2026-11-02, a long-prompt block also takes the router-weight multiply and the add chain after its last expert, so only their sum is read back (paired on the PC, text byte-identical; speed numbers follow in a later release; `src/mc_device.inl`) |
| `MOE_CACHE_HOST_OUT=0` | turn off the direct copy of plugin outputs to the GPU (on by default; RESULTS 76) |
| `MOE_CACHE_EXEC_CHECK=1` | recompute every expert op the stock way and compare (slow; for testing) |
| `MOE_CACHE_TILED_CACHE=1` | audit idea D19, off by default, not measured: the duplicate-expert scan that decides whether llama.cpp would use its tiled routine runs once per ids tensor and graph run instead of for gate, up and down (same answer; per-op saving only for batches with 8+ picks) |
| `MOE_CACHE_FAST_KERNELS=0` | use llama.cpp's own Q2_0 kernel instead of the plugin's |
| `MOE_CACHE_IQ3_KERNEL=1` / `=0` | use the plugin's IQ3_XXS gather kernel (bit-identical) on any AVX2 CPU / turn it off; off by default on AMD, where gathers are slow (Zen 4: slower than llama.cpp's own function) |
| `MOE_CACHE_ROUTE=skip` (`moe-cache-server --fast`; `--fast` also sets a q8_0 KV cache: KL 0.0045 alone on the laptop (CUDA), **0.0120 on the PC (Vulkan)**, `--fast` as shipped 0.0145 there; kept in `--fast` by choice, RESULTS 61 R11) | opt-in approximate routing: skip a low-ranked expert that is not in RAM. Aimed at models much bigger than RAM; about 1 top token in 40-50 differs from stock (KL 0.005-0.012; RESULTS 31). Off by default |
| `MOE_CACHE_HYBRID=MiB\|auto` (`moe-cache-server --hybrid`) | opt-in, experimental: a bank of the most used experts (from the usage profile) in free GPU memory computes those picks while the CPU computes the rest. Flash-Next on 8 GB: KL 0.0043 vs exact (about 1 top token in 60 differs). Needs a usage profile (the first session has none). The bank adapts to the session (`MOE_CACHE_HYBRID_ADAPT=N,K`, default 8,16; 0 = keep the profile choice). For models whose experts are slow on the CPU (IQ / Q2_0 quants); with Q4_K-class models such as Qwen3.6 `--gpu-cache` is the better fit (at 12 GB). Off by default |
| `moe-cache-server --fast=kv` | only the q8_0 KV cache of `--fast`, every expert computed. **Chosen automatically** at `--ctx 131072` and above when a GPU is detected (or `--vram` is given) and you passed none of `--stock`, `--exact`, `--fast*`, `-ctk` / `-ctv`; with no GPU, or at lower context, it is opt-in. It may change answers. Passed the quality gate at 4k context (`docs/reference/quality-gate.md`, level kv: KL 0.0079, top-1 96.7 %, tasks 190 = stock on Flash-Next Q2_0). At ctx 262144 the freed KV buys more GPU layers (RESULTS 72; that pair was measured when `-ub 1024` was the long-context choice; the launcher now picks `-ub 2048` above 32k context when it fits). |
| `MOE_CACHE_FEWER=N` (`moe-cache-server --fast=fewer` sets 2 and `--fast`) | opt-in approximate: on the CPU-held layers, decode and small batches never compute the N lowest-ranked experts of a token (at least half are kept). Passes the gate (level fewer: KL 0.034, top-1 92.0 %, tasks 192 vs 190); passed at 4k, **unproven at 64k-256k** (decode pairs lost their values). Off by default |
| `MOE_CACHE_ROUTE_DROP=N`, `MOE_CACHE_ROUTE_KEEP=N` | with `ROUTE=skip`: how many of the lowest-ranked picks may be skipped (default 2; `--fast=2` sets 4, with at least half of the picks always kept) |
| `MOE_CACHE_COALESCE_MIB=N` | merge neighbouring expert reads of a long prompt into reads of up to N MiB (default 16; 0 = off). Flash-Next prefill measured in RESULTS; speed numbers follow in a later release |
| `MOE_CACHE_SCAN_TOKENS=N` | prompt batches of N+ tokens load experts at the evict-first end, so the cache from before a long prompt survives it (default 512; 0 = off). Flash-Next prefill measured in RESULTS; speed numbers follow in a later release |
| starter profiles (`moe-cache-server --no-starter` to skip) | with no usage profile yet, the launcher starts from the shipped one for the model family (`profiles/`): measured on Flash-Next (RESULTS 53); speed numbers follow in a later release |
| `MOE_CACHE_GPU_PACK=0` | turn off packing: by default a long-prompt block uploads only the experts its tokens use (exact; RESULTS 52; speed numbers follow in a later release) |
| `MOE_CACHE_MAX_RAM_GB=N` | cap on the cache's memory in decimal GB (the launcher's `--max-ram`); 0 turns the default cap off (`src/mc_common.inl`) |
| `MOE_CACHE_WIN_VIEW=0` / `MOE_CACHE_LINUX_VIEW=0` | go back from the file-view cache (read-only views of the model file; the default on Windows since 2026-10-27 and on Linux since 2026-10-28) to private memory with direct reads |
| `MOE_CACHE_QUICKEDIT=1` | Windows: leave the console's QuickEdit mode alone. Without it a real `server` start switches QuickEdit off (a stray click in the window then cannot pause the server's output until a key is pressed) and puts the old mode back when the launcher ends normally; with a killed launcher (`taskkill /F`, window closed) the console keeps QuickEdit off. Set it if you select log lines with the mouse in conhost. | unset (QuickEdit off while a server runs) | Windows users |
| `MOE_CACHE_WIN_OPEN_HINT=sequential` / `random` | Windows A/B switch (default off): open the model file view's handle with `FILE_FLAG_SEQUENTIAL_SCAN` or `FILE_FLAG_RANDOM_ACCESS`, which changes the cache manager's read-ahead for that file. Unset or anything else = the flags used before. Effect unknown (0-5 %, either sign): measure with an A B B A run before using it | Windows only |
| `MOE_CACHE_WIN_BUFFERED=0\|1\|2` | Windows private-memory path only: 0 unbuffered, 1 buffered through the file cache, 2 adds random-access hints (buffered is the default; see platforms.md) |

| `MOE_CACHE_GTM=PATH` | the gputaskman program the benchmark tools read for the environment block of a published number (RAM and VRAM of the whole machine). ## Modes that change tokens: on by default when measured as a win, `--exact` turns all off

Rule of 2026-11-09: there is no opt-in for a speed-up that changes tokens but keeps the meaning. **The default launch is not token-identical to plain llama.cpp (speed numbers follow in a later release).** It enables exactly the rows below whose status is `won` (a paired run shows a speed win and the quality check passed) or `kept` (the quality gate failed, and the owner decided to keep the step on; approximate). A row stays off only when measured `lost` (slower or the meaning changed) or still `unmeasured`. **`--exact` turns every row off** and gives plain llama.cpp's output; it is refused together with `--fast`, `--mtp`, `--long-prompt` and `--approx`. The table lives in `TOKEN_MODES` in `bin/moe_cache_approx.py`; changing a status there changes the default and nothing else (`tests/token_modes_test.py` proves both directions). Exception, owner 2026-11-20: `--kv-4bit` is an explicit opt-in for a memory saving that costs quality (the dense 4-bit KV steps below).

| Mode | Switch | Status | Measured reason |
|---|---|---|---|
| q8_0 KV cache from 128k context | `--fast=kv` (default from 128k) | won | 16 GB card at 256k (speed numbers follow in a later release); gate level `kv` passed, KL 0.0045-0.015 |
| Long-prompt mode from 32k context | `--long-prompt` (default from 32k) | won | Flash-Next IQ3_XXS, 65k, A C C A: speed numbers follow in a later release; meaning kept 10 of 10 at 55k |
| MTP draft head (agent mode, MoE model has the head; a dense model only with `--mtp`) | `--mtp` | won | Qwen3.6 on the PC (speed numbers follow in a later release) |
| Dense model: K q8_0 / V q4_0 KV cache when q8_0 / q8_0 would not fit the GPU (instead of a shorter context) | `--kv-4bit` (off by default since 2026-11-20) | lost (off) | failed the absolute gate level `kv` at 8k-token windows with no floor arm (laptop, 27B UD-Q3_K_XL, one run): KL 0.109, same top token 94.6 %, partly the model's own noise (q8_0 / q8_0 on the same text: 0.063); floor-corrected on Qwen3-30B-A3B (laptop, one run each, forecast): +0.003 to +0.006 KL over the floor at 8k and 32k, which passes; not measured with a floor on the 27B, nothing at 64k. Kept by owner decision; approximate Owner 2026-11-20: off by default (quality cost); opt in with `--kv-4bit`; when q8_0 / q8_0 would spill, the next step is layers to system RAM. |
| Dense model: q4_0 / q4_0 KV cache when K q8_0 / V q4_0 would not fit either | `--kv-4bit` (off by default since 2026-11-20) | lost (off) | failed the absolute gate level `kv` at 8k-token windows with no floor arm (laptop, 27B UD-Q3_K_XL, one run): KL 0.173, same top token 92.9 %, partly the model's own noise; floor-corrected on Qwen3-30B-A3B (laptop, one run each, forecast): +0.022 to +0.040 KL over the floor, over the 0.015 limit in all four cells, so a real cost, the biggest KV cost we ship. PC, 27B 64k: q4_0 fit where q8_0 spilled (one run; speed numbers follow in a later release). Kept by owner decision; approximate Owner 2026-11-20: off by default (quality cost); opt in with `--kv-4bit`; when q8_0 / q8_0 would spill, the next step is layers to system RAM. |
| Skip rarely picked experts | `--fast` | lost | PC, 64k screen of 2026-11-09: no speed win (speed numbers follow in a later release); quality gate passed |
| Skip up to 4 experts | `--fast=2` | lost | PC, 64k screen of 2026-11-09: no speed win at 64k (the laptop result at 12 GB RAM is a different case) |
| Drop the 2 lowest experts on CPU layers | `--fast=fewer` | lost | PC, 64k screen of 2026-11-09: no speed win; quality gate failed |
| Named groups of the rows above | `--approx safe\|careful\|aggressive` | lost (careful, aggressive) | a group is as good as its rows; the PC screen of 2026-11-09 ran careful and aggressive and showed no speed win. `safe` is the q8_0 KV row above; it was not part of that screen |

`--fast`, `--fast=2`, `--fast=fewer` and `--approx` are **deprecated aliases**: they still work and force their modes on, whatever the status.

### The `--approx safe|careful|aggressive` groups (deprecated alias)

**Every tier changes some answers. None is identical to plain llama.cpp's.** Without `--approx` the default launch applies the table above. `--approx exact` means the same as leaving it out. The tiers only group switches that already exist; each mode has a quality gate (the numbers in [QUALITY_GATE](quality-gate.md)) and a list of models it was measured on.

| Tier | Switches it turns on | What changes in plain words | Gate (mean KL at most / same top token at least) | Measured so far |
|---|---|---|---|---|
| `safe` | `kv8` (q8_0 KV cache) + `spec-exact` (the model's own MTP head, only if it has one) | the chat's memory is stored in 8 bit; the model drafts 2 tokens ahead and checks them; every expert is still computed | 0.015 / 95 % | KL 0.0045-0.015; Flash-Next chat same top token 94-95 %, meaning kept 10 of 10 at 55k |
| `careful` | `fast1` (`--fast`, includes the q8_0 KV cache) + `spec-exact` | rarely picked experts that are not in RAM are skipped; about 1 token in 40-50 differs | 0.040 / 90 % | faster; KL 0.0053 to 0.025 |
| `aggressive` | `fast2` (`--fast=2`) + `spec-exact` | up to 4 low-ranked experts per token that are not in RAM are skipped; about 1 token in 28 differs | 0.060 / 88 % (level `fewer`) | Flash-Next at 12 GB faster, KL 0.022 |

| Option | Meaning |
|---|---|
| `--approx-off MODE` | remove one mode from the tier (`kv8`, `spec-exact`, `fast1`, `fast2`) |
| `--approx-unverified` | run a mode that has no gate record for this model (loud line; nobody measured its quality here). A record that says a mode FAILED for this model always refuses it |
| `--no-approx-canary` | skip the startup check below |
| your own `--fast` | wins over the tier's expert mode and is reported; `--exact` and `--stock` are refused together with a tier |

Not in any tier: `--hybrid` (its GPU/CPU rounding changed tokens within 3-20 tokens on a small model), `--fast=fewer`, q4_0 KV (fails the `kv` gate), and modes that are not built yet (relaxed draft acceptance, window-level expert skipping, sparse attention).

**Gate records.** A mode runs for a model only when it has a gate record: the built-in list in `bin/moe_cache_approx.py` (`MODES[...]["verified"]`, from the measurements above; "granite" there is the CI smoke guard only, not a quality statement) or a file `profiles/gates/NAME.json` written by a gate run (`{"match": "model name part", "modes": {"kv8": {"pass": true, "kl": 0.005, "kit": "...", "date": "..."}}}`). Without a record the tier is refused, with the way to go on in the message.

**Startup canary.** After the plan is made and before the server starts, the launcher runs `llama-perplexity` (next to `llama-server`) on `tools/approx_canary.txt` (prose, code, French and German, numbers, SQL; two chunks of 256 tokens, about 256 scored tokens) with this launch's own placement flags, once with the exact setting and once with the tier, and compares the KL divergence and top-token share with the tier's gate. If the tier is past its gate it is stepped down one tier (aggressive, careful, safe, exact) and the server starts with that; the line says so. The result is stamped per model file, plugin library and tier, so later starts do not measure again (state in the cache folder, `approx/`). The first start of a big model costs two extra model loads. If the canary cannot run (no `llama-perplexity`, a failed run) the tier runs as asked and the launcher says nothing was checked. **A canary guards, it never proves**: passing it does not make a mode a default.

## Settings not listed above (checked against the code on 2026-11-03)

The table above is the short list. This part covers the remaining `MOE_CACHE_*` names the code reads, found with `tools/env_names_check.py` (it lists every name in `src/`, `bin/` and `planner/` and whether a doc mentions it; `--missing` shows only the gaps). "Who" says who should touch it: **everyone**, **advanced** (you know what the option does), **internal/testing** (for the project's own tests and experiments; leave alone), or **set by the launcher** (the launcher sets it for the plugin; do not set it by hand). Switch values: where a row says "1/on/true/yes", those four turn it on.

| Variable | What it does | Default | Who |
|---|---|---|---|
| `MOE_CACHE_ALLOW_SLEEP` | Lets the computer go to sleep while the server runs. Set to `1`, `true` or `yes` (same as `--allow-sleep`). Normally the launcher holds a sleep block so a long run is not cut off. | off (sleep is blocked while the server runs) | everyone |
| `MOE_CACHE_STOCK_WHEN_FITS` | Set to `1` to run plain llama-server for a model that fits in memory even when some layers keep their experts on the CPU (the same as `--stock`). By default such a model runs through the plugin's expert executor, which was NOT faster in the release check on a laptop with an 8 GB GPU (paired 40k chat: decode not faster, prompt reading slower); an earlier decode gain was not reproduced and is retracted (CHANGELOG, FAQ). | off (the plugin runs in that case) | everyone |
| `MOE_CACHE_DENSE_SPILL_RULE` | On Windows, a dense model whose plan still spills out of GPU memory at 128k context or more gets `-np 1` (one request at a time) and `-ub 256` (half the compute buffer) by default. On our test PC (27B UD-IQ4_XS, 128k, one A and one B run, a forecast): prompt and decode faster; at 64k the same rule lost on prompts, so it stays off below 128k. Other systems: off (not measured there). `1` forces it on from 64k up (any system), `0` turns it off. Not with `--exact` or your own `-np` / `-ub`. | on at 128k+ on Windows | everyone |
| `MOE_CACHE_INKLING_OP_OFFLOAD` | Looped models (Inkling 2, or any model whose GGUF has `loop.count` > 1) only: by default, when experts are on the CPU, the launcher adds `--no-op-offload` and `-ub 128` (nothing changes when all experts are on the GPU), because the staging copy of the shared loop-layer experts is about 4 GB at Q2 and does not fit an 8 GB card, and older llama.cpp builds gave NaN with it. `0`, `false`, `no` or `off` = always add `--no-op-offload`; any other value = leave op offload on (llama.cpp's own default). Your own `--no-op-offload` / `-nopo` after `--` also wins. | off (`--no-op-offload` added) | looped-model users |
| `MOE_CACHE_LOOP_FIT` | Test switch (off by default) for looped models: set to `1` and the launcher turns op offload on when the llama.cpp build is b12642 or newer (it has the fix for shared loop weights) and the staging copy fits the planned GPU compute budget, and picks `-ub` 512, 256 or 128 as the largest that fits that budget. Never at 128k+ on a dense model (measured as a loss, planner/never_list.json). | off | testers |
| `MOE_CACHE_TUNE_THREADS` | Test switch (off by default): set to `1` and the first-start auto-tune also measures two threads fewer than the plan (`-t`). Not with your own `-t` or `--leave-room`. | off | testers |

| `MOE_CACHE_CLASSES` | Number of usage classes for the `classlru` cache policy (only used when `MOE_CACHE_POLICY=classlru`). Clamped to 2 to 8. Has no effect with the plain `lru` policy. | 4 | advanced |
| `MOE_CACHE_CPU_MASK` | Hex bitmask of CPUs (bit i = CPU i) the expert worker threads are pinned to. Overrides automatic pinning. Does nothing if `MOE_CACHE_CPU_PIN=off`. | unset (automatic on hybrid Intel CPUs) | set by the launcher |

### Names that are not run-time settings

These appear in the code but setting them in the environment does nothing (build-time macros, test build flags, shell variables inside the launcher script, or a name with no code behind it).

|---|---|
| `MOE_CACHE_EXPORT` | Not an environment variable: an internal build macro that marks functions as exported from the plugin library. Nothing to set. |
| `MOE_CACHE_FEWER_RENORM` | Not read by any code. A comment says it is not implemented; setting it does nothing. See `MOE_CACHE_FEWER` and docs/reference/quality-gate.md for the working feature. |

| `MOE_CACHE_TEST_MUTANT_PACK_OFFSET` | Not a runtime variable: a compile-time flag (`-D`) used only by CI. It copies expert slices from a wrong offset so the pack identity test is proven able to fail. Never set it. |
| `MOE_CACHE_TEST_NO_POPULATE` | Not a runtime variable: a compile-time flag (`-D`, `src/platform.h`) used only by CI to test the guarded page-touch that a kernel without `MADV_POPULATE_READ` takes. Never set it. |

## Measured auto-tune

| What | How |
|---|---|
| When | The first real start for a model file + this machine (CPU, cores, RAM, GPUs, llama-server build) + context. `--dry-run`, `--plan-json` and the control page's plan never measure; they show the stored pick |
| What it tries | The plan as it is; then the edge walk: one more expert layer on the GPU per load (`--n-cpu-moe` -1, -2, ...; 2 layers per load while a known fit limit is more than 6 layers away, stepping back one layer once when a 2-layer step fails) until a load fails (the layer count right before a failed load is not picked: it leaves less than the reserve free), on Windows the planner's fit limit is reached (a model that does not fit spills there instead of failing to load; the limit is the same sizes with a smaller reserve: `--gpu-margin` / `--leave-room` or the desktop's reserve, else none on the AMD / Intel room figure and 0.25 GB on another; the step at the limit is not picked either; when the limit equals the plan, as it usually does with the desktop's reserve on an NVIDIA card, no walk runs and the end line says so), decode falls more than 5 % below the best step, the commit check would refuse the step, no layer is left on the CPU or the time runs out; then up to 2 of: a doubled `-ub` (only from a small plan, up to the probe prompt's length: 512 -> 1024), 2 more expert layers on the CPU, `MOE_CACHE_RAM_LOCK` + `MOE_CACHE_DROP_READAHEAD` (Linux plugin), `-np 1`. Never the KV type and never a micro-batch above the 1.5k probe prompt: the long-prompt defaults (`-ub 4096`, q8_0 KV) were measured at 65k and a 1.5k probe cannot judge them. A setting you gave (flag before or after `--`, or the environment variable) is never tuned |
| Budget and probe | At most 180 s in total, loads included. Per plan: a ~1.5k-token prompt (prompt tok/s) and 512 generated tokens (decode tok/s); when the time left is short the decode is shorter and the line says "short probe". The probe ranks plans; it is not a 64k figure |
| Pick | The lowest time for a 1,000-token prompt (a chat turn: earlier turns come from the prompt cache, so decode counts most) (16,000 in agent mode) plus 512 generated tokens; a plan must beat the plan as it is by 5 % and by more than twice the plan's own spread between its two runs, else that one stays. The plan as it is runs twice (noise check), and the leader runs a second time (confirm run): the slower of its two runs must still win. A leader with no time left for its confirm run is not picked. Only the leader gets a second run: there is no time in 180 s for two runs of every plan |
| Not tuned | A model bigger than the memory the server may use (the default 75 GB model on most machines): one line says so and nothing is loaded. A model whose first load takes over 60 s: that load is stopped at 60 s, the plan as it is stays and nothing is stored (the next start tries again, usually with the file in the page cache). A stored pick is still used |
| Windows commit check | Every command that is loaded to measure has passed the commit check first; a plan it would refuse or shrink is not loaded (`--no-commit-check` is respected). If the memory guard stops a probe, the whole tuning is aborted, nothing is stored, the plan as it is runs and the next start tries again |
| Where | `<cache dir>/autotune/<key>.json` (`~/.cache/moe-cache` on Linux). The key covers the model, context, machine, user-flag set, tuner version, the launcher version, the llama.cpp build, the memory caps, the modes (`--fast`, `--mtp`, `--approx`, long-prompt, `--hybrid`), `--cache-ram` and the KV type of the plan; the picked expert-layer count is stored with the plan it was measured from and replayed as that layer count; it is not replayed when the plan of the day already puts as many layers on the GPU, never past the day's fit limit, and a pick that adds GPU use needs about as much free GPU memory as when it was measured |
| Lock | One tuning at a time: `<cache dir>/autotune/tuning.lock` (the launcher's pid and time; a dead holder's or older than 10 min is taken over). A second start while one is measuring runs untuned this time, says so, and looks the pick up again at its next start |
| A pick that does not load | The stored pick is applied at every start, so one that stops llama-server before it is ready is marked bad in its file and the plan as the planner made it starts once. The next starts run that plan and say the pick is bad; `--retune` measures again. A server that was ready and died later is not a bad pick |
| Redo / skip | `--retune` measures again. `--exact` and `--stock` skip it (one line says so: `auto-tune: off (--exact)`; the same for `MOE_CACHE_NO_AUTOTUNE`). While `--retune` measures, the first line says it is measuring again, not that this is the first start. `MOE_CACHE_NO_AUTOTUNE=1` is for scripts and benchmark arms (the bench tool sets it) |
| A plan as it is that cannot be measured | (it stops while loading, or the probe fails) Stored as "too slow": not tried at every start; `--retune` tries again. A load over 60 s is not stored this way (above) |
| Output | Launcher lines `moe-cache: auto-tune: ...` including `trying plan N of M` while it measures and a line when the commit check changes the picked plan (the control page lists them under "What the launcher decided", live while the server is "starting") and the `autotune` object in `--plan-json` |
