# moe-cache v0.3.8 (release date: pending)

**What this release is.** Long prompts are read faster by default, the launcher picks the best layout for the context you ask for (never a shorter one) and tunes small models on the first start, the Windows launcher refuses a start that would take the machine down, the control page and a terminal monitor show what the engine is doing, Claude Code works on Qwen3.8, and the kits bundle our patched llama.cpp build with every patch off. Flash-Next IQ3_XXS is the default model again. **Every number below is filled from the release night on this v0.3.8 kit; a blank `{{RN: ...}}` means the number is not in yet, and no number from an earlier version is reused.**

**Answers are not token-identical to plain llama.cpp's by default.** The default switches on only the speed-ups that won their paired runs: long-prompt mode from 32k context (q8_0 KV cache, `-ub 4096`), q8_0 KV from 128k and for dense models, MTP drafting in agent mode. The meaning is kept (same-meaning checks: {{RN: KL, same top token %, quality gate result on this kit}}), the exact tokens can differ. **`--exact` gives plain llama.cpp's answers** (it turns every one of them off, MTP included); on the control page choose the **Exact** mode. Modes without a measured win (`--fast`, `--approx`) stay off.

llama.cpp pin: b12207 (commit `998200491`, ggml 0.29.0, backend API 3), moved from b12064.

## What changed

| Where | Change | Measured |
|---|---|---|
| Long-prompt mode, **on by default** | From 32k context on a graphics card with room the launcher reads prompts in chunks of 4096 tokens (`-ub 4096`) with a q8_0 KV cache and `MOE_CACHE_GPU_MIN_TOKENS=64`; all three are part of what was measured. `--no-long-prompt` goes back to `-ub 2048` and f16 KV; `--exact` gives plain llama.cpp's answers. Approximate modes (`--fast`, `--approx`) stack on this plan instead of switching it off (LAUNCHER-985). | Flash-Next IQ3_XXS, 65k conversation, previous default against long-prompt: prompt {{RN: long-prompt prompt tok/s and %}}, decode {{RN: long-prompt decode tok/s and %}} |
| Token-changing defaults | One table (`TOKEN_MODES` in `bin/moe_cache_approx.py`) decides what changes answers: the default turns on exactly the modes that won (long-prompt mode, q8_0 KV from 128k and for dense models, MTP in agent mode); expert skipping (`--fast`) and the `--approx` tiers are unmeasured and stay off. **`--exact` turns every one of them off** and is refused together with `--fast`, `--mtp`, `--long-prompt` and `--approx` (LAUNCHER-984). | none |
| Auto-tune, **on by default** | On the first real start for a model, machine and context the launcher tries 2-4 plans for at most 180 s, keeps the fastest if it beats the plan by 5 % and remembers it. **It tunes models under 40 % of RAM only**; a bigger model, such as the default Flash-Next, is not tuned, and the output says so. Every probe passes the Windows commit check, a guard stop aborts the tune and stores nothing, the KV type is never changed. `--retune` measures again; `--exact`, `--stock` and your own flags win (LAUNCHER-994, 1042-1044). | {{RN: auto-tune pick against the plan, a model under 40 % of RAM, on this kit}} |
| Windows commit guard | Before the load the launcher estimates the commit of the whole llama-server (GPU buffers, copied weights, prompt cache) and, when under max(6 GB, 12.5 % of the commit limit) would stay free, tries smaller layouts first (mmap, smaller `-ub`, smaller prompt cache, q8_0 KV, more weights in RAM; never a shorter context), else refuses and says what to close or how big the page file should be (`--no-commit-check` skips it). While the server runs a guard polls free commit, warns under the soft line and stops llama-server cleanly under 2 GB. Cause: on AMD drivers GPU memory counts as commit, and big models at 64k-128k context took Windows down. On Linux the guard polls available memory and only warns by default (`MOE_CACHE_COMMIT_GUARD=stop\|warn\|off`). After a guard stop there is no second load (LAUNCHER-991, 1029). | {{RN: commit-guard check on the PC: 27B at 128k refused or planned smaller, no crash}} |
| Dense models | A dense model is planned for the context you ask for, never a shorter one: q8_0 KV before any spill, then `--fit` or the FFN-in-RAM plan; the dedicated GPU is picked automatically; the log is scanned for work placed on the CPU the plan did not expect. A model that runs out of GPU memory at load (a game or browser took memory after the plan) is planned once more, one step smaller, instead of aborting (LAUNCHER-850, 982, 983). | PC, Qwen3.8-27B at 64k, f16 against q8_0: {{RN: 27B 64k decode}}. Laptop OOM retry on this kit: {{RN: live check, GPU memory taken after the plan, loaded after one retry}} |
| Models that fit in RAM | A MoE model that fits in RAM but has expert layers on the CPU runs through the plugin's expert executor; `--stock` or `MOE_CACHE_STOCK_WHEN_FITS=1` opts out. A model whose experts all fit the GPU still runs stock; with no GPU it stays stock. | Laptop with an 8 GB GPU: {{RN: laptop fits-in-RAM decode and prompt}}. 16 GB PC, plugin forced: {{RN: Qwen3.6-35B ratios}} |
| Control page and terminal | **Monitor view**: live speed, context depth, cache hit rate (overall and per layer), SSD, memory against the cap, executor share, the plan as it runs, a searchable log (GUI-041). **Mini window** (⧉ Mini, 360 x 480). **`moe_cache.py top`**: the same data in the terminal, seven views, read only (GUI-044..048). Live counters for approximate modes (GUI-042); **at-risk marks** under each answer that show which steps changed routing (GUI-043); an **audit (exact)** button that re-scores the last answer with an exact-mode server and shows where it could have gone another way (GUI-043). The audit runs only when clicked. The Monitor costs one `/metrics` request every 2 s (`MOE_CACHE_MONITOR=0` turns it off). | Decode with the Monitor open against closed: {{RN: monitor cost, A B B A}} |
| Control page | Default mode follows the command line (long-prompt mode, q8_0 KV, MTP); **Exact** is a separate mode that passes `--exact`; a page that had saved "exact" from before the Default mode existed becomes Default once (LAUNCHER-993). The page finds models in `~/models` and, on Windows, `\models` on every fixed drive, the same list as the picker (GUI-1052). | none |
| Agents | **Claude Code on Qwen3.8**: the Qwen3.8 chat template rejected a system message after the first turn (HTTP 500 "System message must be at the beginning"); the launcher now gives llama-server a copy of the model's template with one line fixed (your own `--chat-template*` wins). `connect claude --check` tests exactly this (AGENTS-992). | none |
| Plugin | No crash on models with 512 experts: the long-prompt GPU block is sized from the real tensor count (CACHE-988). | {{RN: Nemotron 3.5 Super load and first answer, PC}} |
| Default model | Flash-Next IQ3_XXS is the default again; Q2_0 is the faster option. | {{RN: IQ3_XXS prompt and decode ratio of stock}} |
| llama.cpp kit | The Windows kit and the Linux `-ggml0.26` tarball bundle our patched llama.cpp build (b12207 plus patches 0004, 0020, 0030, 0040). **Every patch is built in and off.** The launcher prints which patches are in at start-up. CI checks that the build answers like the official one at temperature 0. The official build still works. | no speed change claimed |
| Benchmarks | The benchmark tools live in the launcher: `bench-report --chat`, the Fair comparison button, a ready-to-measure panel, a noise verdict, the results view, `--limit-gb`, and a submit flow (`bench-record ingest-issue`). | tooling, no speed claim |
| CI | Downloads in the CI workflows retry and use the cache first; the Windows job checks the template fix and the model-folder query. | none |
| Windows | The scheduling tuning (EcoQoS off, raised CPU and GPU priority) is removed: two paired repeats measured it slower. `--no-sched-tuning` is accepted and does nothing for one release. | {{RN: decode and prompt with the tuning on, from the WINDOWS-013 records}} |
| Archived | Switches and patches that did not win a paired run moved to `archive/` with restore notes. | none |

## Known limits

The README "Known issues" table lists them. In short: auto-tune measures only models under 40 % of RAM and was first measured on {{RN: machines where auto-tune was measured}}; the commit-guard estimates are calibrated on one Windows PC and the Linux guard only warns by default; the plugin-for-fits default is measured on one 8 GB-GPU laptop and one PC model; the dense-model rules are laptop only; the `-ub 4096` memory estimate comes from one model, so another model may need the one automatic retry or `--no-long-prompt`.
