# moe-cache v0.3.8 (release date: pending)

**What this release is.** Long prompts are read faster by default, the launcher picks the best layout for the context you ask for (never a shorter one) and tunes small models on the first start, the Windows launcher refuses a start that would take the machine down, the control page and a terminal monitor show what the engine is doing, Claude Code works on Qwen3.8, and the kits bundle our patched llama.cpp build with every patch off. Flash-Next IQ3_XXS is the default model again. **Every number below is filled from the release night on this v0.3.8 kit; a blank in double curly braces means the number is not in yet, and no number from an earlier version is reused.**

**Answers are not token-identical to plain llama.cpp's by default.** The default switches on only the speed-ups that won their paired runs: long-prompt mode from 32k context (q8_0 KV cache, `-ub 4096`), q8_0 KV from 128k and for dense models, MTP drafting in agent mode. The meaning is kept (same-meaning checks: {{RN: KL, same top token %, quality gate result on this kit}}), the exact tokens can differ. **`--exact` gives plain llama.cpp's answers** (it turns every one of them off, MTP included); on the control page choose the **Exact** mode. Modes without a measured win (`--fast`, `--approx`) stay off.

llama.cpp pin: b12207 (commit `998200491`, ggml 0.29.0, backend API 3), moved from b12064.

## What changed

| Where | Change | Measured |
|---|---|---|
| Long-prompt mode, **on by default** | From 32k context on a graphics card with room the launcher reads prompts in chunks of 4096 tokens (`-ub 4096`) with a q8_0 KV cache and `MOE_CACHE_GPU_MIN_TOKENS=64`; all three are part of what was measured. `--no-long-prompt` goes back to `-ub 2048` and f16 KV; `--exact` gives plain llama.cpp's answers. Approximate modes (`--fast`, `--approx`) stack on this plan instead of switching it off (LAUNCHER-985). | Flash-Next IQ3_XXS, 65k conversation, previous default against long-prompt: prompt {{RN: long-prompt prompt tok/s and %}}, decode {{RN: long-prompt decode tok/s and %}} |
| Token-changing defaults | One table (`TOKEN_MODES` in `bin/moe_cache_approx.py`) decides what changes answers: the default turns on exactly the modes that won (long-prompt mode, q8_0 KV from 128k and for dense models, MTP in agent mode); expert skipping (`--fast`) and the `--approx` tiers are unmeasured and stay off. **`--exact` turns every one of them off** and is refused together with `--fast`, `--mtp`, `--long-prompt` and `--approx` (LAUNCHER-984). | none |
| Auto-tune, **on by default** | On the first real start for a model, machine and context the launcher tries 2-4 plans for at most 180 s, keeps the fastest if it beats the plan by 5 % (or by twice the plan's own run-to-run spread, if larger) and remembers it. **Not yet measured on the PC at the time of writing; the release night adds it.** **It tunes models under 40 % of RAM only**; a bigger model, such as the default Flash-Next, is not tuned, and the output says so. Every probe passes the Windows commit check, a guard stop aborts the tune and stores nothing, the KV type is never changed. `--retune` measures again; `--exact`, `--stock` and your own flags win (LAUNCHER-994, 1042-1044, 1041, 1045). A stored pick that stops the server before it is ready is marked bad and the plan as made starts once; one tuning at a time; the stored pick's key covers the cache size, MTP, the approximate modes and the KV type. | one laptop (i7-13620H, RTX 4060 8 GB), Qwen3-14B Q4_K_M, first start 164 s of the 180 s budget, picked -ub 1024 against the plan's 512 (probe prompt 967 against 136 tok/s; a ranking probe, not a 64k figure), reused from the cache on the second start |
| Windows commit guard | Before the load the launcher estimates the commit of the whole llama-server (GPU buffers, copied weights, prompt cache) and, when under max(6 GB, 12.5 % of the commit limit) would stay free, tries smaller layouts first (mmap, smaller `-ub`, smaller prompt cache, q8_0 KV, more weights in RAM; never a shorter context), else refuses and says what to close or how big the page file should be (`--no-commit-check` skips it). **The commit estimate is measured on one AMD Windows PC only.** While the server runs a guard polls free commit, warns under the soft line and stops llama-server cleanly under 2 GB. Cause: on AMD drivers GPU memory counts as commit, and big models at 64k-128k context took Windows down. On Linux the guard polls available memory and only warns by default (`MOE_CACHE_COMMIT_GUARD=stop\|warn\|off`). After a guard stop there is no second load (LAUNCHER-991, 1029). | {{RN: commit-guard check on the PC: 27B at 128k refused or planned smaller, no crash}} |
| Dense models | A dense model is planned for the context you ask for, never a shorter one: q8_0 KV before any spill, then `--fit` or the FFN-in-RAM plan; the dedicated GPU is picked automatically; the log is scanned for work placed on the CPU the plan did not expect. A model that runs out of GPU memory at load (a game or browser took memory after the plan) is planned once more, one step smaller, instead of aborting (LAUNCHER-850, 982, 983). | PC, Qwen3.8-27B at 64k, f16 against q8_0: {{RN: 27B 64k decode}}. Laptop OOM retry on this kit: laptop, Qwen3-14B Q4_K_M: another process took 3.5 GB of the GPU after the plan, the first load failed, the launcher retried once with the FFN of 35 of 40 layers in RAM (was 11), loaded and answered |
| Dense models, KV cache ladder | For a dense model the launcher picks the KV type from the free GPU memory it measured, each step only when the one before would spill: f16, then q8_0 / q8_0, then K q8_0 / V q4_0, then q4_0 / q4_0, and only then layers to RAM; the context is never shortened. The plan line names the step and the GiB it saves. **The quality and speed figures come from one laptop run and one PC run so far; no published records exist yet.** `--exact` keeps f16; your own `-ctk` / `-ctv` win. On Windows a dense model that fits fully on the GPU loads with `--load-mode none` (no RAM spike from the mmap copy; seen on one PC run, no published record yet) (LAUNCHER-1063, 1068). | Quality against f16 (27B): laptop, Qwen3.8-27B UD-Q3_K_XL, 8 windows of 8192 tokens from real chats, against f16 KV: same top token q8_0 / q8_0 96.5 % (KL 0.063), K q8_0 / V q4_0 94.6 % (0.109), q4_0 / q4_0 92.9 % (0.173); on the 202-task set q8_0 KV scored 181/202 and q4_0 KV 182/202; PC decode with q8_0 spilling against q4_0: {{RN: 27B 64k decode, desktop on the card}}; RAM at load: {{RN: PC peak, mmap against none}} |
| Models that fit in RAM | A MoE model that fits in RAM but has expert layers on the CPU runs through the plugin's expert executor; `--stock` or `MOE_CACHE_STOCK_WHEN_FITS=1` opts out. A model whose experts all fit the GPU still runs stock; with no GPU it stays stock. | Laptop with an 8 GB GPU: decode +10 to +29 % in six paired band comparisons (mean +15 %), prompt about 10 % lower. 16 GB PC, plugin forced: {{RN: Qwen3.6-35B ratios}} |

## Known limits

The README "Known issues" table lists them. In short: auto-tune measures only models under 40 % of RAM and is not yet measured on the PC at the time of writing (the release night adds it: one laptop only; the PC has none yet); the commit-guard estimates are calibrated on one AMD Windows desktop, not yet checked on NVIDIA or Intel (the rule that NVIDIA on Vulkan counts GPU memory as commit is an assumption), and the Linux guard only warns by default; the plugin-for-fits default is measured on one 8 GB-GPU laptop and one PC model; the dense-model rules are laptop only; the `-ub 4096` memory estimate comes from one model, so another model may need the one automatic retry or `--no-long-prompt`.
