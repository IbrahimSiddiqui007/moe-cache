# moe-cache v0.3.9 (release date: pending)

**What this release is.** The kits bundle our build of llama.cpp b12651 (ggml 1.0) — the pin move that lets looped models (Inkling 2 Mini / Small) launch. The dense KV cache ladder stops at q8_0 unless you opt in to the 4-bit steps with `--kv-4bit`. A MoE model that nearly fits the graphics card now runs stock llama.cpp, which is as good or better there, and the launcher says so. `--exact` also turns off the model card's sampling defaults and the chat-template fix. Auto-tune covers more models and is stricter about what it keeps. The launcher writes its plan to a data file, sizes the plugin's RAM from the RAM that is really available, and the version line names the commit. **This release ships before the speed re-record: there is no stock-against-moe-cache table, no headline speed claim, and every measured speed figure appears as a {CLAIM:...} placeholder until the re-record day fills it.**

**Answers are not token-identical to plain llama.cpp's by default.** The default switches on only the speed-ups that looked like a win in our runs: long-prompt mode from 32k context (q8_0 KV cache, `-ub 4096`), q8_0 KV from 128k and for dense models, MTP drafting in agent mode. The meaning is kept (the same-meaning checks of the previous release still stand; no new quality-gate result on this kit), the exact tokens can differ. **`--exact` gives plain llama.cpp's answers** — since v0.3.9 it also turns off the model card's sampling defaults and the chat-template fix, so the answer is what plain llama.cpp gives (it turns every mode off, MTP included); on the control page choose the **Exact** mode. Modes without a measured win (`--fast`, `--approx`) stay off. The dense KV ladder now stops at q8_0: the K q8_0 / V q4_0 and q4_0 / q4_0 steps come only with `--kv-4bit`, and `--exact` keeps f16.

llama.cpp pin: b12651 (commit `f5e6915c2`, ggml 1.0.0, backend API 4), moved from b12207. The kits bundle OUR build of that commit (every patch built in and off); the temperature-0 identity check compares it with an unpatched build of the same commit that CI builds itself. The Windows kit ships `ggml-moe-cache-api4.dll` next to the api2 and api3 ones; the older b12207 official build stays available with `LLAMA_SERVER`.

## Measured

**No speed comparison against plain llama.cpp in this release.** The speed numbers are being re-recorded on the bundled b12651 build; until then no stock-against-moe-cache line is claimed for the default model, Q2_0 or Qwen3.6-35B, and measured figures appear only as placeholders. What exists, named with its machine and run count:

- Bundled build against the previous kit, our test PC (27B, 128k, one run per arm, forecast): decode {CLAIM:bundled-vs-official}. No prompt-speed claim is made for the new build.
- The long-prompt default's figures, measured on the earlier b12064 build and re-recorded on this kit (Flash-Next IQ3_XXS, 65k conversation, one run per arm, forecast): prompt {CLAIM:conv-iq3xxs-prompt}, decode {CLAIM:conv-iq3xxs-decode}.
- The Windows dense-spill rule (27B UD-IQ4_XS, 128k, one run each, forecast): prompt and decode {CLAIM:dense-spill-128k}. It stays off below 128k and on other systems (not measured there).

The laptop checks named in the table below (auto-tune, the GPU expert cache, the live RAM follow, the dense quality floor test) are one machine and few runs each; most v0.3.9 launcher changes are built and not measured yet. A one-run figure is a forecast, not a verdict. Test PC: Windows desktop, Ryzen 9 7950X, RX 9070 XT 16 GB, 32 GB RAM at 6000 MT/s (EXPO), Vulkan. Older per-depth records on the earlier head kit are in `docs/RESULTS_CURRENT.md`; they are not v0.3.9 numbers.

| Launcher / plugin | **A plugin build for another ggml API is not loaded into a server it does not fit**: the launcher first looks for another installed llama-server (the kit's own first) that fits, else plans the stock path, or stops when you asked for the plugin. A llama-server you named is kept and the line names the matching one. | none |
| Launcher | **Op-offload batch 512 is set only for a MoE stock run with expert layers on the CPU** (not a dense layer split); on a dense model it measured faster prompts with it unset and equal decode. | One laptop, dense 27B, 8.9k prompt, A B B A, one machine, forecast; figures pending re-record |
| Launcher / first run | **First-run clarity (Windows install / agents):** `launch --dry-run` shows step 5; the printed commands use `moe-cache` when it is on the PATH; the plain-chat step names `launch --agent` and `connect`; a "fatal error" line from a KV type llama.cpp refuses is explained as handled; the "attention on the CPU" warning no longer blames one cause. | none |
| Launcher / plugin | **The version line also names the commit**: `moe-cache --version` prints `moe-cache 0.3.9 (commit abc123456)`, and the check header and the plugin's start-up line carry it too, so a log says which build ran. A release kit has the commit in a `BUILD_COMMIT` file; a checkout asks git (`-dirty` = local changes). | Log text only; built, Linux tested, not run on Windows |
| Installer / launcher | **An install in its own `-Root` (Windows) or `--prefix` (Linux release install) keeps its own settings, API key, chats, reports and on-demand files in `<root>\cache\moe-cache` / `<prefix>/cache/moe-cache`** instead of sharing the user cache. Only NEW installs get it; an older install keeps the user cache after an update. `XDG_CACHE_HOME` set by you still wins. | Built and unit-tested; not run on a real Windows PC |
| Launcher | **Stored auto-tune picks and GPU load records survive a copy**: they were keyed by file modification times, so a re-unpacked kit or a copied model measured everything again; the key is now the files' content (whole-file hash up to 256 MiB, sampled hash above). | After this update every model is measured once more |
| Launcher / Windows | **A dense model that spills out of GPU memory at 128k context or more now runs with `-np 1 -ub 256` by default on Windows** (one request at a time, half the compute buffer); it stays off below 128k and on other systems. | Plugin | **`MOE_CACHE_ROUTE=subst` is removed**: it put a different resident expert's weights in place of a picked expert that was not in RAM, and never had a quality measurement. Setting it now prints one line and routing stays exact. `MOE_CACHE_ROUTE=skip` (`--fast`, off by default) is unchanged. | none |
| Launcher | **Review fixes:** `--flag=value` after `--` is read as `--flag value` (llama.cpp rejects the equals form); `--port` must be 1-65535; `--max-ram 0.00` means no cap and `inf` is refused; `--override-tensor` counts like `-ot`; the commit guard sees the flags you give after `--`; `launch` exits 130 when a signal ends the server and stops the server it started on a wait error; a retracted decode claim was removed from the configuration docs; the docs no longer carry ledger codes, internal notes or private paths. | none |
| Launcher / Windows | **Opt-in: a dense model's memory-mapped load becomes `--load-mode none` when the whole file would leave less than the reserve** (`MOE_CACHE_MMAP_SPIKE=1`; OFF by default): with it on, the launcher counts the whole file plus the prompt cache against the RAM available now and picks `none` when less than the reserve (max(4 GiB, 12.5 %)) is left; one plan line says why. Not for MoE models, Linux, `--exact`, `--stock` or a load flag of your own. | Built, not measured |
| Plugin / launcher | **The cache follows the system's available RAM while the server runs, where its experts are private memory** (Windows by default; Linux only with `MOE_CACHE_LINUX_VIEW=0`; on Linux's default file-view cache it is OFF): the plugin reads available RAM every time it tunes, evicts experts under the keep line (`MOE_CACHE_AVAIL_KEEP_GIB`, max(4 GiB, 12.5 % of the RAM)) and grows the budget back by at most 256 MiB a second. It can only give back the cache's own memory. A `moe-cache: mem:` line every 15 s shows the figures. The 1 GiB, 256 MiB, 250 ms and 500 ms constants are assumptions. | Partly measured on the laptop (n=1: the `mem:` line and the grow path were seen with private memory on Flash-Next; the shrink path was not triggered); Windows build only syntax-checked |
| Launcher / RAM | **The plugin's RAM is sized from the RAM available at start, on Windows and Linux**: one decision function gives the cache `available RAM - max(4 GiB, 12.5 % of RAM)`, and 2 GiB less when the model file is bigger than the cache (`MOE_CACHE_STREAM_GIB` changes that term). **Linux default changed:** every Linux plugin start now gets a smaller expert cache than before (about 4 GiB, or 12.5 % of RAM on big machines, less), possibly slower decode on a machine with free RAM; the Linux speed numbers were measured with the old size. `--ram`, `MOE_CACHE_RAM_GIB`, `--stock` and a Linux cgroup limit are unchanged. | Built, not measured; not run on the PC yet |
| Launcher / GPU cache | **`--gpu-cache auto` is now the default on Linux with a CUDA llama-server** for a MoE model that fits in RAM and runs the stock engine with expert layers on the CPU side: llama.cpp's own GPU expert cache, `-ub 2048`, `--load-mode none`. It stays off on Windows, Vulkan and every other backend, for dense models, with the plugin engine, a draft model or MTP, and with `--gpu-cache off`, `--exact`, `--stock`, `--hybrid` or your own `--n-cpu-moe`, `--moe-cache-mib` or `-ot`. No speed claim is made here. | One NVIDIA laptop and one model only |
| Launcher / GPU cache | **A GPU expert cache that does not fit is retried once without it**: after a failed load with a cache the launcher itself chose, it starts once more with the static GPU plan and remembers the size that failed (the next start plans 15 % under it); after two failures in a row it plans no cache. Your own `--moe-cache-mib` after `--`, `--exact` and the plugin engine get no retry. | Built, laptop checked, one machine |
| Launcher | **The launch plan is written as a data file and printed on start**: for each setting the launcher decides, the value, where it came from (probe / measured / constant / user / llama) and one plain reason. Real starts write `<cache>/plans/port-PORT.json` (removed when the launcher ends); `--plan-file PATH` writes it with `--dry-run` too, `--plan-json` carries it. The final `--n-cpu-moe` is shown on the stock path as well. No launch command changes. | 122 recorded plan cases identical |
| Launcher / GPU plan | **One GPU placement, from what llama-server really used**: the first-placement formula no longer decides `--n-cpu-moe`; one function plans from the model's own weights, the KV cache, the compute buffer and what the free-memory figure overstates. A real start stores llama-server's own buffer sizes for this GPU, build and model (`MOE_CACHE_LOAD_RECORD=0` turns it off); without a record the tables are used and the plan file says "constant". The auto-tune walks `--n-cpu-moe` down one layer per load from the plan until a load fails or decode falls clearly below the best step; still at most 180 s. Follow-ups: MTP loads recorded with the draft context told apart, out-of-memory loads remembered per GPU / driver / build / model / context / micro-batch for 30 days, the driver version in the record key, `--leave-room` keeps its 2 GB on the Windows AMD / Intel room path. | Built, not measured on a real load yet |
| Release tooling | **Release archives are written reproducibly** (archive layer only): sorted entries, fixed file user, group and permissions, the commit's date (`tools/reproducible_zip.py`); the publish check needs all seven release files; the bundled llama.cpp licence is pinned by its sha256. | The compiled programs inside are not proven byte-identical |
| Windows / launcher | **`--no-sched-tuning` is removed** (it has done nothing since v0.3.8): a command line that still has it is refused as an unknown option, so delete it from old start scripts. | none |

## Known limits

The README "Known issues" table lists them. In short: most v0.3.9 launcher changes are built and not measured yet, or measured on one laptop only (auto-tune changes, the GPU expert cache default and its retry, the live RAM follow, the Linux RAM sizing, the dense 4-bit KV quality cost, the dense spill rule); the Inkling 2 launch path was checked for the correct answer on one 8 GB laptop with an earlier llama.cpp build, not as a release result on the bundled kit, and no speed figure is claimed for it; the bundled b12651 build has one forecast decode figure against the previous kit and no prompt-speed claim; the speed tables are re-recorded on the new build after the release; after this update every model is auto-tuned once more; the Linux expert cache is smaller by default than in the previous release.

## Update

`moe_cache.py update --apply`, or run `install.sh` / `install.ps1` from this release.
